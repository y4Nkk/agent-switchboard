# Agent Note: 备份与会话的显式清理及更新包残留清扫

Status: implemented

## Problem

[本地资源的有界读取与显式回收](2026-10-14-bounded-local-resources.md) 落地后，应用内可回收的只有可重建缓存与可归档历史；`backups/` 目录随每次切换、恢复、扩展与端口操作持续增长，`sessions/claude.sqlite3` 保留库只增不减（仅有单会话删除，删除后数据库文件不缩小）。[Claude 会话保留库](../bug-fix/2026-10-22-claude-account-session-retention.md) 的决策是长期保留正文，但没有给出"用户想整体瘦身"时的路径。此外 tauri-plugin-updater 在 Windows 上启动安装器后直接退出进程，`%TEMP%\{app}-{version}-updater-*` 目录永远不会被插件自身清理，长期使用会积累无主安装包。

## Decision

备份清理、会话清理与更新包清扫共享同一原则：**回收始终是用户显式触发的维护操作，不引入自动按量或按天删除**。[有界回收](2026-10-14-bounded-local-resources.md) 的既有决定继续成立——本篇只扩大显式回收的覆盖面，不改变"可用性优先于磁盘硬上限"的取舍。

备份清理沿用历史归档的两阶段契约：预览生成 `BackupCleanupPlan`（截止日期、文件数、字节数、内容摘要），执行时先重扫校验摘要，再把选中备份族流式写入用户选定的标准 `.tar.gz`（强制在应用数据与缓存目录之外）。清单作为 tar 内的 `manifest.json` 条目；导出后逐条回读名称、类型、长度和内容哈希，确认材料与计划一致，并再次核对本地内容后才原子发布和删除本地副本。不存在 JSON 前缀包、旧格式解码或只检查文件存在的成功判定。

选择以**备份族**为单位：认证记录的 `linked_backup_id` 指向配置记录 ID，选择器按反向关系把认证 `.bak` 与其元数据并入主配置；客户端设置快照路径由 `LocalState` 统一提供，保存、恢复与清理都使用 `backups/client-settings/`。这些成员同进同退，最新配置的保护覆盖全部成员。独立扩展目录备份与 gateway-port 目录副本作为整体目录单元；没有有效元数据的配置 `.bak` 文件及其元数据保留，带无法识别元数据的目录同样保留，不把恢复材料拆开回收。存在 pending 事务日志时整体拒绝执行；执行持有配置写入门禁，与切换事务互斥。

会话清理经由保留库所有者：预览和执行统一使用已有会话元信息的 `last_active_at`，取顶层与子会话的最大活动时间；`saved_at` 只表示捕获时间，不参与清理日期判定。活动时间未知的会话保留。执行先扫描同步，再推导候选，逐个复用组织数据清理、`history::delete` 来源删除、墓碑与孤儿资产回收。删除门内再核对当前截止日期资格及原文件修订，刚更新或在捕获后被改写的会话保留并报告具体原因。截止日期仍是唯一调用契约，预览数字只作参考，不使用全库计划摘要。删除完成后执行 checkpoint 与 VACUUM，失败作为警告；Codex 原生历史不纳入。

同日（2026-10-28）用户划定存储模块边界后，本篇有三处归属修订：其一，会话清理的入口从存储面板迁到「会话记录」页——存储与缓存只承担本软件自身的维护（缓存、旧安装包、旧配置），不清理 Claude/Codex 内容；批量清理命令随归属移入会话命令域，`session_manager` 保留库所有者身份不变，删除语义（含原始会话记录）不变。其二，历史归档收窄为本软件的配置写入历史：Codex 请求账本与雷达检测记录不再经由存储归档回收（CodexRequestLedger/ProbeLedger 的归档导出与剪除路径删除；雷达记录删除由检测页既有入口拥有）。其三，备份清理的入口从存储面板迁到「备份恢复」的「备份清理」页签——备份是备份恢复域的事实，清理紧挨恢复链与撤销入口；回收能力仍属存储维护（命令留在 storage 域），两阶段导出契约与保护红线不变。

更新包清扫在启动时以独立线程执行：按与应用相同的包名前缀匹配 `%TEMP%` 下 `{name}-*-updater-*` 目录，修改时间超过 7 天即删除，单项失败静默忽略（正在安装的负载被系统锁定，会随安装完成自然消失）；仅在实际删除时记录一条运行时事件。该清扫是自动的，因为它只触碰本应用留在系统临时目录的安装残留，不触碰任何用户数据。

存储设置页承载历史归档流程（截止日期、预览、确认与回执）；备份清理是「备份恢复」的第三个页签，会话清理入口在会话记录页工具行，同一预览-确认-回执结构，确认文案平实说明会话清理会同时删除客户端目录中的原始会话记录。

## Alternatives considered

- 自动保留策略（保留最近 N 份备份/天数）最省用户操作；但直接推翻 [有界回收](2026-10-14-bounded-local-resources.md) 明确记录的"全部文件备份受保护"决定，且自动删除恢复链在任何故障场景下都难以向用户交代，因此本次只提供显式入口，自动策略留待真实需求出现再评估。
- 备份直接删除不导出最快，也与用户在资源管理器手工删除等价；但备份是唯一的本机恢复材料，先导出后删除与历史归档流程保持同一可恢复标准，成本只是一次写出。
- 会话清理做全库计划摘要对账可以固定预览集合；但后台捕获可能更新不相关会话，不应让整个批次因此失效。采用执行时重算与逐会话删除门校验，范围变化只影响实际变化的会话，不能跳过活动时间和修订检查。
- 只删除保留库副本、保留客户端原始文件看似更保守；但单会话删除的既有语义就是来源与副本一起删除，双语义会让"删除"在同一界面出现两种结果，因此批量清理继承单会话语义并在确认文案中明说。
- 清扫 `%TEMP%` 时放宽到所有应用的更新残留能多回收空间；但触碰其他应用的文件超出本应用边界，因此只匹配自身包名前缀。

## Consequences

- `backups/` 的批量回收入口在「备份恢复」页签，`sessions/` 的批量回收入口在会话页；两者仍随使用增长，不引入任何自动删除，[有界回收](2026-10-14-bounded-local-resources.md) 的结论（业务恢复可用性优先于磁盘硬上限）不变。
- 云端快照恢复出的历史记录若指向已被清理的备份，撤销会得到明确的 `backup-not-found` 错误而非静默失败；这是清理的固有代价，备份页的打开文件夹入口仍是手工兜底。
- 会话清理删除的会话经墓碑机制不会被捕获线程重新导入；删除前导出仍走会话页既有的导出入口，清理流程不重复提供导出。
- 更新包残留有 7 天保留窗，正常更新节奏下用户不可感知；系统临时目录的其余内容由操作系统拥有。
- 回归用例覆盖真实单向认证关联、最新组所有成员的保护、设置快照共用路径、标准 tar 解析、归档损坏拒绝、同长度内容变化拒绝、目录材料与空目录、活动时间与捕获时间的区别、未知与新活动保护、未捕获改写及新增子会话。删除用例只传入隔离目录扫描所得的来源，备份用例持有既有客户端路径隔离门禁；不读取或删除真实客户端会话。归档收窄后的旧账本与雷达导出路径仍保持删除。按 AGENTS.md，本任务不执行编译、类型检查或自动化测试，不能把新增用例当作通过证据。
