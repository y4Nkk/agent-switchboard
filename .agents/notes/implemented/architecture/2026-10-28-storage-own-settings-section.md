# Agent Note: 存储与缓存升级为设置独立分类

Status: implemented

## Problem

「存储与缓存」最初是偏好设置面板底部的一段卡片（上边框分隔，跟随 AppSettingsForm 与出口代理之后）。随着容量总览之外新增了历史归档与浏览器缓存清理两组维护操作（备份清理与部分归档范围当日即按模块边界迁出，见[备份与会话的显式清理](2026-10-28-storage-reclamation-expansion.md)），它在偏好设置里既拉长了页面，又与偏好开关（即时生效的单字段设置）性质不同：存储是低频、批量、有确认流的数据维护入口，埋在偏好底部不利于发现，也让偏好设置承担了第二套内容形态。

## Decision

设置工作区新增一级分类「存储与缓存」（`SettingsSection` 新增 `storage` 值，排在「备份恢复」之后），`StorageSettings` 整体迁出偏好设置，改为与备份恢复/诊断同构的独立面板：内容自渲染 `asb-panel` + `ModuleHeader`，挂在 `SettingsPage` 自己的 tabpanel 下；偏好设置不再渲染存储内容。分类页签与面板标题同用 `storage.title` 一份命名（存储与缓存），与其他分区「页签名 = 面板标题」的既有约定一致。

- 分类清单仍由 `navigation.ts` 的 `SETTINGS_SECTIONS` 唯一拥有，页签、tabpanel 与标题都从它派生；分区状态仍是内存态（不持久化），新增枚举值不涉及旧值迁移。
- `active` 语义不变：容量读取只在进入「存储」分类时发起，离开即停止；归档/清理成功后的快照刷新回调保持原有接线。
- `.asb-storage-settings` 原有的上边框分隔样式（为"偏好底部尾段"设计）删除，面板形态下分隔由 `asb-panel` 卡面承担。

## Alternatives considered

- 升级为侧边栏主导航一级工作区被否：存储是低频维护功能，撑不起常驻主导航位（本次需求也明确只做主界面二级界面）。
- 并入「用量监控 → 资源占用」被否：该页签拥有本机编码进程的运行时采样（CPU/内存/进程），磁盘容量与维护按既有契约由存储管理独立拥有，混入会打破两条事实边界。
- 并入「备份恢复」被否：存储面板保留的缓存清理与历史归档同备份恢复无归属关系；会话清理与备份清理随后按同日划定的模块边界（只做本软件自身维护）分别落回会话记录页与「备份恢复」的「备份清理」页签，见[备份与会话的显式清理](2026-10-28-storage-reclamation-expansion.md)。
- 独立全屏弹层/路由被否：设置分区页签就是本应用二级界面的既有结构，另造一层导航形态没有收益。

## Consequences

- 设置分类从五个变为六个：偏好设置、客户端工具、备份恢复、存储与缓存、诊断、关于；偏好设置回到纯偏好开关与出口代理。
- 面板头部标题由 `ModuleHeader` 拥有；面板描述覆盖容量、缓存与归档清理操作。`DESIGN.md` 设置清单、存储条目与双语 README 的入口路径已同步。
- 本次请求未要求编译、类型检查或自动化测试；页面结构以源码审查与既有同构面板（备份恢复）为依据，桌面验收需运行确认。
