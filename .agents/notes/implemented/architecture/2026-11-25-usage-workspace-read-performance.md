# Agent Note: 用量工作区的读取性能

Status: implemented

## Problem

请求性能的分页和定时更新都重复计算完整报告。供应商额度按行读取同一份文件，消费报告重复遍历日桶，雷达历史先聚合再分页。资源页等待原生采样，Windows 的界面进程发现还要等待界面线程。

## Decision

- 请求性能由本地读取器持有当前不可变报表快照。时间、客户端、计量范围和模型决定汇总，后续分页按快照里的记录身份和已排序分组取页，IPC 只传回两种分页内容。SQLite 为指定和未指定客户端分别使用已有索引。分位数用顺序统计选出原插值所需的两个值。
- 消耗统计以只读连接取得已核实快照，刷新任务流式读取现有日桶，同时产生四个范围的报告，共享覆盖统计。来源检查、已核实前缀和持久快照由现有索引拥有。
- 供应商额度一次读取现有缓存并投影当前档案。资源重进即显示带采样时间的旧结果，原生采样重新建立 CPU 区间。Windows 同时等待各窗口的 WebView2 进程关联，再交给原生采样。雷达先选当前历史页，再聚合该页批次的运行结果。
- 五个页签在本地通过 User Timing 分开标记打开反馈和首批数据，用开发工具读取。

## Alternatives considered

- 把性能事件和分组数据传到界面再分页，能简化后端快照生命周期。消息体和界面内存会随历史增长，且明细不需要跨进程传输。
- 使用分位数草图能降低长范围计算的内存占用。现有报表承诺对原始样本精确插值，固定数量的顺序选择保留精度。
- 维护一张新消费汇总表能压低某些冷读取的工作量。已有事务日桶承担增量维护，新表会增加写放大和跨范围会话去重维护。

## Consequences

同一性能快照的页码变化不重算汇总，同范围自动更新或手动刷新生成新一代快照。性能快照按记录身份保留当前筛选的明细定位，内存随单次结果的身份数量增长。档案与原始历史的持久格式保持现行结构。首次索引或采样仍取决于本地数据规模和系统行为，桌面端按页签记录反馈与数据两段时间。
