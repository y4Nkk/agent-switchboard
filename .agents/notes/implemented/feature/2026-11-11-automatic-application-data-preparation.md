# Agent Note: 启动准备与应用数据自动修复

Status: implemented

## Problem

应用数据异常此前由用户点击「一键智能修复」后处理。用户需要先看到错误、找到入口，软件才执行本来已经能判断的修复。应用偏好还有独立修复按钮，启动时只显示等待偏好和侧栏读取的骨架，没有统一的准备状态、处理阶段与失败去向。

原有启动并不是一个可以直接加按钮回调的空入口：`lib.rs` 在 setup 中初始化存储、网关、事务恢复及后台服务；`useSwitchboardModel` 在 App 判断是否显示骨架之前就挂载多个数据读取 hook。因此，在 React effect 中自动调用旧修复命令会与初始化、读取及其他写入交错，也无法展示 setup 尚未返回时的工作。

现有修复能力也不完全适合无人确认执行。`ConfigStore::repair` 使用暂存目录、完整校验与原目录备份，但目录交换的进程中断没有独立的持久恢复记录；`LocalState::repair_app_settings` 直接写默认偏好，没有保存损坏原件；`outbound_proxy::repair` 将无效文件移为备份后使用默认直连；供应商修复还可能删除不受支持的自定义端点。自动化前必须明确这些动作各自的边界。

## Decision

`application_preparation` 是原生端唯一持有的应用准备流程，统一启动检查与运行期间的自动修复。前端观察状态、显示进度及诊断，不再拥有「检查到错误后执行修复」的决策。使用确定性的现行规则，不引入模型调用或联网判断。

自动准备处理当前应用拥有的配置目录和明确可恢复的偏好问题；连接策略无法确定、事务冲突或业务原件损坏时保留数据，结束尝试并报告所属功能不可用。自动执行不意味着把所有错误都重置成默认值。

### 启动顺序与所有者

1. 保留单实例守卫。窗口创建前只执行必要的偏好读取及既有明确版本升级，以确定语言、WebView 硬件加速等创建时设置。失败保留原件并进入可见的准备/诊断界面，不能因此提前覆写文件。
2. 注册准备状态和写入闸门，创建能够显示准备页的最小窗口。耗时的配置处理放到后台执行，使 setup 可以返回并让 WebView 绘制；需要主线程的窗口、托盘操作仍回到原线程执行。有效的启动最小化偏好继续生效，需要处理的错误则显示主窗口。
3. 核实配置目录与待恢复事务。存在已确认事务时交给现有事务所有者，并保留其网关等前置依赖顺序；通用数据修复不能绕过、删除或重命名恢复标记。前置依赖不足就报告该域受阻，不能用修复结果冒充事务恢复完成。
4. 先严格检查，只有检查明确命中允许的修复规则才建立暂存副本。修复、严格回读、原件修订复核、启用及备份继续归原领域所有者；正常启动不对有效配置整目录复制，也不产生无变化的备份。
5. 相关域完成后再开放其消费者、网关请求和后台写入。出站策略没有有效结论时不开放依赖它的联网请求。终态明确区分可以完整进入、可以进入但部分功能不可用、只能留在诊断界面三种情况。

准备流程只顺序调用具体领域函数，不建立可插拔修复注册表。`ConfigStore`、`LocalState`、`outbound_proxy` 和现有事务执行器继续拥有各自文件及有效性规则，准备流程不再保存一份配置事实。

### 自动处理边界

| 数据/情况 | 建议行为 | 不自动执行的动作 |
| --- | --- | --- |
| 当前结构中的 BOM、缺失 automatic 意图、现有可无歧义交接的设置字段 | 在暂存副本修复，完整校验后启用并保留原目录 | 宽松运行时读取、删除未知字段或跳过坏档案 |
| 已有明确版本识别的应用偏好升级 | 复用专属升级器，升级前保留原件；普通读取继续严格 | 根据相似字段猜版本，永久双读旧结构 |
| 偏好 JSON 无法解析 | 仅在能读取并完整保留原件、确认属于应用偏好文件后，写入经验证的当前默认偏好并明确报告；有效 JSON 的未知、不完整及语义非法结构保留并报告 | 因权限/占用错误覆写文件，或者连带清理连接、凭据、档案、历史 |
| 主地址中现行规则已经明确识别的 Anthropic 末尾版本段 | 继续由端点所有者校验修复前后地址，修复报告列出变化 | 推测其他 URL、协议、模型或密钥 |
| 不受支持的自定义端点候选 | 保留原件并报告无法确定；该配置域不能被标为修复成功 | 为通过校验静默删除候选或改向其他地址 |
| 出站代理设置无效或不可读 | 保留原件并报告；依赖该策略的联网请求保持不可用，设置编辑继续可达 | 静默改为直连、继承环境代理或改用其他代理 |
| 已知可重建派生索引/缓存 | 继续由现有索引所有者按需恢复；不等待全部历史重建后才进入 | 把会话保留库、收藏、用量事实库当成可丢弃缓存 |
| 未知旧结构、无法解析的业务文件、并发修改、磁盘满、备份失败、事务冲突 | 保留原件，报告具体阶段、文件和原因；停止本次尝试 | 清空目录、自动选择某份旧备份、忽略失败后显示成功 |

偏好恢复默认是一个明确、可见的恢复结果，不把成功解析的任意字段拼成一个猜测出来的契约。有效偏好不改动。原件无法读取或文件身份无法确认时，该默认恢复规则也不成立。

出站设置和端点候选这两项收窄改变了旧手动修复的行为，已同步修改原有决策笔记、命令和 UI。用户仍可在原设置编辑器明确修改连接设置；这与要求用户点击修复按钮是不同职责。

现有已确认切换事务的恢复仍由原执行器处理，可能涉及其已授权的客户端文件。新增通用自动修复只写应用自有状态，不获得新的客户端配置写权限，也不重新应用供应商、更新安装、重新登录或重跑真实请求。

### 中断、并发与重试

配置目录启用前，由 `ConfigStore` 持久记录本次修复的暂存目录、原目录备份、内容修订和提交阶段，并同步落盘。恢复记录严格接受当前 version 1，路径从唯一标识推导；进程在两次目录 rename 之间退出时，下次启动必须先核对这份记录与两边实际内容，再完成启用或恢复原目录，不能把暂时缺失的 live 目录当成全新安装创建空存储。

恢复记录只描述该领域的一次未完成交换；成功且回读通过后结束记录。目录身份、内容或提交阶段不匹配就保留全部材料并报告，不能靠文件名排序选择「最新备份」。偏好原件备份、默认文件发布与失败恢复也必须覆盖对应的中断窗口。

应用内写入继续遵守现有 `ConfigWriteGate`、桌面偏好锁和代理写入锁；不同时占有跨领域锁并反向请求另一领域，防止初始化与运行期修复形成锁顺序环。文件系统操作在后台执行，提交前复核来源版本；原件变化就丢弃旧修复候选。

同一进程的应用数据准备只有一个自动检查/修复任务。启动、受管文件变化和重新检查共用它；以实际文件修订标识输入，同一份失败输入不因 focus、轮询或重复错误无限重试。文件内容/身份变化后重新检查；I/O 问题在本次检查中明确结束，条件变化或用户重新检查才再次处理，不保留第二条手动修复执行链。

### 状态与启动界面

准备状态快照由后端单一持有：进程身份、本次运行标识、递增修订、运行/完整就绪/部分可用/受阻状态、当前阶段、单调已用时间、逐域结果及修复文件/备份/错误报告。状态观察不依赖尚未初始化的领域管理器，窗口重建后读取同一快照。

使用短状态读取请求观察活动流程，终态停止调度；初次读取即返回当前快照，不依赖前端必须及时收到某个事件。前端拒绝较旧修订覆盖新结果；卸载只停止观察，不取消正在提交的原生修复。

准备页沿用 ASB 的标志、主题、字体和窗口控件，中心内容为「正在准备 Agent Switchboard」、后端阶段说明、不定量进度及已用时间。当前只交付阶段及单调时间，不制造总量或百分比。正常快速启动不设强制停留时间；大历史的按需索引继续由所属页面展示，不制造全历史阻塞。

偏好尚不能确定语言时沿用既有的无文案骨架，解析或恢复后再显示对应语言；避免先绘制一套语言再跳变。计时放在局部组件内，尊重减少动态效果偏好，屏幕阅读器不逐秒播报。

完整成功自动进入用户设置的启动页面；部分可用自动进入外壳并显示一条可展开的结果，禁用受影响的功能及写入，而不是显示空数据冒充成功。真正受阻时结束加载，留在诊断页提供具体原因、查看日志/原件位置和退出；只有暂时性失败提供重新检查。退出必须经过原有退出守卫，提交临界区完成或回滚后才能结束进程。

### 直接变更位置与旧路径删除

- `src-tauri/src/lib.rs`：拆开最小窗口启动与后台准备；明确管理器发布和消费者开放时序，保留已确认事务恢复顺序及正常退出守卫。
- `application_preparation` 模块及状态读取、重新检查命令：拥有一次流程、修订、逐域可用性和去重；命令在领域尚未发布时返回类型化的未就绪状态，不以 `app.state` 缺失导致 panic。
- `src-tauri/src/config_store/repair.rs` 及交换所有者：复用现行修复规则，补充中断恢复、严格前后校验和端点候选拒绝；有效状态不复制。
- `src-tauri/src/local_state/caches.rs`、偏好升级器与 `src-tauri/src/outbound_proxy.rs`：补齐偏好备份和恢复边界，统一代理无效状态的处理；删除自动/手动路径之间不同的重置语义。
- `src/App.tsx`：在独立的准备边界之后才挂载拥有 `useSwitchboardModel` 的业务组件；初次准备完成后才挂载业务 hooks。业务快照、设置、更新及探测等直接消费者按域就绪状态启用。
- `src/components/GlobalInformation.tsx`、`src/app/useApplicationDataRepair.tsx`、`src/app/useAppSettings.ts`、代理设置组件：移除成功路径依赖的修复按钮和 UI 编排，统一消费自动准备结果；连接编辑、诊断和重新检查保留原所有者。
- 已删除无人调用的 `repair_application_data`、`repair_app_settings`、`repair_outbound_proxy_settings` IPC、浏览器开发分发、前端包装和旧词条；内部能力移到唯一领域调用链，不保留兼容命令。状态命令同时接入桌面和浏览器开发入口。
- `README.md`、`README.zh-CN.md`、`DESIGN.md` 与受影响笔记同步记录当前行为。

### 运行期观察与退出

原生监听只观察状态根的直接变更与配置目录的递归变更，忽略访问事件及无关历史写入。输入内容修订去重，监听失败会重建观察器；无法恢复时显示具体错误并允许重新检查。健康检查保持静默，实际恢复才展示覆盖层；业务树保持挂载，覆盖层使背景不可交互并接管、恢复焦点。

请求串行合并；读取期间的再次通知排队重读。进程身份与修订共同避免迟到状态覆盖新结果，同一修订的计时观察不重绘业务树。完成代次仅用于触发原有消费者重读。检查后不能把随后外部改写的修订记为已验证，修复完成还要再走一次当前严格读取。

检查生命周期独立于可见忙碌状态，静默检查也持有执行归属。退出保留原退出码并等待当前检查/提交结束；停止期间不接受新检查。原有会话、更新、雷达与网关恢复守卫仍生效，退出被阻止后恢复同一准备流程。正常有效输入没有修复写入，旧手动入口和日志别名均删除。

## Alternatives considered

- **启动后在 `useEffect` 自动调用现有修复按钮回调**：代码最少，也能复用当前通知与刷新。但业务 hooks 已经提前读取，原生服务也已启动；重复挂载可能再次执行，且直接带入无备份偏好覆盖和代理直连重置。因此不采用。
- **把所有修复同步放在 Tauri setup 中**：状态依赖简单，可以保证业务命令启动前完成。不过耗时工作发生在可观察界面之外，不能实现截图中的真实阶段与等待说明。因此只保留必要的创建时偏好读取，重工作放到可观察的原生后台流程。
- **无效文件统一备份后恢复默认，原样复用旧修复语义**：恢复可用性的覆盖面最大，也最接近无人操作。但默认网络出口、端点候选和供应商身份不是可以互换的界面偏好，备份只能保证材料可找回，不能证明自动改变业务含义正确。因此仅对明确的非业务偏好采用可见的默认恢复。
- **启动先扫描并修复全部历史**：完成后每个页面都已有数据，用户只面对一处等待。但会把可用启动绑定到历史规模，重复已有按需增量所有者的工作。因此启动只守住当前契约和写入一致性，历史处理继续增量进行。

## Verification

用户明确授权隔离测试并要求不启动开发机器浏览器。`scripts/test-application-preparation.py` 在独立 USERPROFILE、HOME、APPDATA、LOCALAPPDATA、CODEX_HOME、CLAUDE_CONFIG_DIR 与临时目录中运行，移除调用凭据和代理环境，保留只读构建工具链与缓存。48 项聚焦测试覆盖当前数据零修复写入、备份字节、规则修复与拒绝、原生文件监听、请求合并、退出等待、外部改写和并发修订。

同一测试二进制的隔离子进程在偏好记录/备份/暂存/发布，以及配置准备/待交换/原目录移出/副本启用共八个位置直接退出，随后通过生产数据准备函数恢复。八组均核验原件备份、当前读取、恢复标记清理、重复运行零写入及隔离客户端哨兵不变。ignored 的子进程入口由此实际执行，不是遗漏的验收。

`scripts/test-application-preparation-ui.mjs` 在 Node 中渲染真实组件，对中英文、阶段与计时、受阻诊断、转义、部分结果、语言骨架、业务树延后挂载和减少动态效果完成 22 项断言。共享语言存储以同一当前语言提供服务器快照，仅为无浏览器渲染所需；没有另建语言来源。前端类型检查与生产构建、全部原生测试代码的编译通过；笔记结构单独校验。

证据不等于真实桌面/跨平台视觉、真实客户端配置恢复、真实网络或大历史规模验收。本次没有启动桌面/WebView/浏览器，没有使用真实业务配置或凭据，也没有提交、发布或部署。

## Consequences

自动化将修复纳入启动，因此目录与偏好恢复记录、输入修订和幂等边界与代码一并落地。新增的是一个小型协调所有者及可观察状态，代价是初始化需要显式暴露依赖顺序；不应借此重写所有领域或增加通用任务框架。

保留业务含义意味着无法保证所有坏数据都自动变成可用数据。部分代理或档案问题将保留原件、停止自动尝试，并要求用户在原有编辑入口明确修改真正的连接设置；不能通过恢复默认值掩盖这一限制。
