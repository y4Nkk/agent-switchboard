# Agent Note: 更新占用守卫只认可证实的运行映像

Status: implemented

## Problem

客户端更新的占用守卫复用监控的用户范围契约：候选名进程的属主无法核实即中止整个更新准备。商店版 Codex 桌面应用自带 SYSTEM 沙盒服务（`CodexSandboxService.OpenAI.Codex`，服务名 `codex-windows-sandbox-service.exe`，开机自启），WTS 对非提权调用者不给该进程属主 SID，进程恒为 Unverified，含 "codex" 的服务名又命中守卫候选网，于是「准备更新」恒以 `Cannot verify process {pid}: EnumerationRestricted` 失败——只要桌面应用装着，npm 版更新永远无法进行，英文枚举 Debug 串还直接漏进界面。

监控侧对同一类进程早有明确裁决（[原生进程资源监控](../architecture/2026-10-23-native-process-resource-monitor.md)）：共享服务不因前缀认领、未核实候选只形成枚举覆盖提示。守卫的「无法核实即致命」与之矛盾：同一进程，监控判为无关边界，守卫判为致命阻断。

## Decision

占用判定只认可证实的运行映像。守卫改为「候选名 → 直接读映像路径 → 路径命中安装目标或其进程根 → 才阻断」，判定不再经过用户范围与出生身份：占用是文件事实，不是用户事实，其他用户的进程占用目标安装文件同样阻断。

安装目标、进程根与已读到的运行映像共用 `identity::canonical_root` 规范化，避免一侧解析链接、另一侧只替换路径分隔符而漏掉占用。Claude 的数字版本映像名仍属于候选；其 npm 主包和声明的平台包、原生版本目录与标准入口共用这一套判定，桌面缓存、其他安装和路径不可读的候选不因名称相似而阻断。

三平台新增守卫专用的枚举与探测面（`resource_monitor/platform` 各平台的 `process_images` / `image_path`），不借用监控 `Reader`：

- Windows：ToolHelp 快照给候选名；`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW` 按调用者权限读映像路径，查询失败保留为未知。
- macOS：`proc_listpids` 全量列表 + `proc_pidpath` 按调用者权限读路径。
- Linux：全量 `/proc` 目录 + `exe` 链接（需要对该进程的读权限）。

读不到映像路径一律跳过：不构成阻断，也不构成归属，更不能据此断言属于其他安装。删除旧的「枚举 issue 即致命」分支与 `Cannot verify …` 错误串。守卫不再调用监控 `Reader`（其初始化、用户核实、出生身份与占用判定无关）；`birth()` 保持原样，供任务启动握手使用。候选网保持宽于监控的引擎识别（前缀与安装文件名兜住 `codex-x86_64-…` 等平台载荷映像）。

占用错误由 `client_software/error` 的 `SoftwareError::ProcessInUse` 唯一拥有，携带客户端与 PID；预览、启动提交、安装前后台复验均保留该类型。命令边界转换为现有 `CommandError`，任务错误转换为共享 `LocalizedMessage`，前端统一按 `software.processInUse` 和参数渲染中英文，不解析英文诊断串或再次包进通用 detail。

任务日志当前格式为 version 2，`UpdateTask.error` 只接受结构化消息或 null。[操作日志当前契约](../architecture/2026-11-09-current-operation-journals.md)取代读取时隐式升级的决定：旧版本、字符串错误及非法结构明确拒绝并保留原文件，不新增兼容或过渡入口；任务身份、阶段、修订、进程出生身份继续由当前结构保存，不从历史文案猜测占用者。

守卫的同一条生产判定循环接收候选列表与路径探测函数，确定性测试覆盖两端候选路径不可读时放行、跳过不可读候选后仍拦截可证实占用、Claude 数字版本映像、npm 平台包根、外部安装放行、候选过滤与整体枚举失败。链接路径用隔离 Unix 符号链接夹具覆盖，不要求 Windows 创建链接权限。真实进程回归测试对 Codex 和 Claude 分别复制临时命名进程。错误序列化、两端后台任务落盘与旧格式拒绝有对应夹具，前端同一错误对象覆盖中英文切换。

## Alternatives considered

- 保持「无法证明空闲即停止」并要求用户提权或停服务：最强的理由是它忠实于旧契约字面且绝对保守；但该条件在装着商店版桌面应用的机器上恒真（服务开机自启，而用户级 npm 更新本不该要求提权），等于功能永久失效。旧契约与监控笔记对同一进程的裁决已经矛盾，保守没有事实基础，不采用。
- 按监控的父链归属判定占用（服务不是引擎所以不认领）：最强的理由是与监控身份规则完全一致；但守卫要回答的是文件占用而非软件归属，父链判定需要完整拓扑与根核实，映像路径直接回答「是否占用这些文件」，更简单且更准（恰好在安装根下运行的 SYSTEM 进程也能被路径逮住），不采用。
- 只把 `codex-windows-sandbox-service.exe` 加白名单：改动最小；但按名单打补丁正是 2026-10-23 笔记否决过的路（`codex-*` 前缀误认的教训），任何新的服务名都会复发，契约不收敛，不采用。
- 在前端识别或替换英文占用字符串：最强的理由是改动集中、无需改变后端错误传播；但后台复验会持久化同类错误，字符串解析使文案同时成为协议且丢失类型约束，不采用。现有结构化消息承担同一份运行时和落盘契约。

## Consequences

- 收益：不再因候选属主未知而永久拒绝准备更新；占用提示在即时错误与后台任务中均使用当前界面语言，客户端和 PID 保持结构化；守卫决策有隔离的确定性与真实进程回归用例。
- 代价：无法读取的目标映像及 macOS 截断列表仍可能漏拦，不能宣称所有安装器或平台必然通过文件锁报错兜底。整体枚举失败仍中止；若需要保证未知情况下也能阻断，必须重访当前只按肯定证据拦截的决策。旧格式日志不再自动恢复，原件保留，读取错误阻止在未知任务状态下启动新安装。
- 更新准备、启动提交与安装前后台复验共用本守卫，三处保留相同的占用错误类型。
- 历史只读调查（2026-11-09）：PID 10524 为该 SYSTEM 服务，`Get-Process` 与 WMI 均无法读取其路径；该证据不等价于新增原生函数的运行验收。开发机按项目验证纪律不执行编译与自动化测试，隔离夹具和编译交由远程四平台共用门禁；修复后的真实客户端更新与界面准备流程仍需本机验收。
