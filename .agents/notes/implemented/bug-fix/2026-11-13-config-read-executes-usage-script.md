# Agent Note: 配置读取不执行用量脚本

Status: implemented

## Problem

当前 Claude 通用供应商读取、保存、完整快照校验和修复校验调用 `usage_query::validate_persisted`；它不仅验证持久字段，还构造 QuickJS 上下文并执行脚本初始化。初始化以 250 毫秒单调墙钟时间限额运行，进程调度暂停也消耗该预算。任何初始化错误都转成固定的脚本对象错误，再被通用供应商读取映射为配置格式错误。Codex 专用存储已只使用核心字段校验，两端约束实际不同。

真实当前配置的隔离副本无需改动任何字节：原生完整读取驱动在 25 次各 400 毫秒的受控子进程暂停下，9 次读取产生三次格式错误，归属 Zhipu GLM 与 DeepSeek 的 Claude 供应商文件，原因均为脚本初始化错误；前后全部配置哈希相等。诊断只暂停本任务创建的子进程，不暂停真实安装或自然静置中的开发进程。具体本机文件位置仅保留在忽略目录的诊断证据中。

另一真实历史备份的四个 Claude `modelOptions.routes` 缺失问题可独立复现，但相关文件已在 11 月 12 日 14:32 转换，而截图生成于 16:49 与 17:25，不能用这一旧格式代替后续运行时误报的解释。旧通知没有调用和文件日志，不能证明每一次历史发生都由同一个暂停事件引起。

## Decision

持久化契约由 `asb-core::validate::validate_usage_query` 唯一拥有：校验当前 tagged JSON 字段、来源文本非空与长度限制、刷新间隔，以及声明式请求的字段规则。供应商读写、完整快照和修复都通过现有 profile/file 校验调用这一所有者，删除桌面层重复的 `validate_persisted` 路径。

JavaScript 的语法、初始化、函数形态和执行结果在真正测试或调度查询时由既有 `ScriptProgram` 校验，继续保持内存、栈和时间限额。无效或超时脚本仍使查询失败并保留上次成功读数，不能使供应商 JSON 变成坏配置，也不能触发配置目录修复。两端写入接受同一持久化契约；不缓存校验结果、不增加旧格式读取或回退，不修改现有脚本、凭据、连接或刷新策略。

导入来源同样直接使用核心字段校验，不能因执行资源失败而丢弃原脚本。查询执行器区分运行环境初始化失败、程序初始化失败和已触发的时间限额；限额消息由同一预算常量生成，保留静态诊断，不回显脚本异常值。

配置错误显示真实文件及原始失败原因：普通读取、自动修复和恢复记录共用 JSON 诊断格式，保留解析器给出的缺失字段、实际类型、预期结构与可用行列位置，隐藏错误中引用的字符串值及未知枚举输入，不再把全部结构失败压成一个分类。Serde 对内部标记枚举等结构不一定提供坐标，此时保留真实字段错误，不虚构行列。文件读取失败保留操作系统错误文本和错误号，不仅保留 `ErrorKind`。此处只改变错误传递，不增加格式兼容或第二套校验。全局持续错误、准备结果和普通错误通知统一保留后端诊断；翻译摘要未包含诊断时追加详情，已包含时只显示一次。

## Alternatives considered

- 增大时间预算最容易降低当前机器的误报频率，但不能让配置有效性独立于负载，也不能处理脚本初始化中的时间或随机行为，故不采用。
- 缓存一次成功的脚本校验能避免重复执行，但引入缓存修订与失效路径，仍将初次资源失败误归到文件；因此直接删除读取时执行。
- 只在保存时执行脚本可早反馈部分语法问题，但仍让 Claude 与 Codex 写入采用不同于读取的契约，并使保存依赖机器负载；统一保留字段校验，执行反馈由既有测试查询提供。
- 只显示 JSON 错误分类最容易避免回显字段值，但会隐藏缺少哪个字段、预期什么类型；保留解析器原诊断并在展示边界隐藏其引用值，可以提供原因且不复制格式校验器。

## Verification

错误详情补齐后的源码另通过 91 项相关原生测试及 34 项中英文渲染检查。测试把实际配置读取命令、Claude `routes` 反序列化错误和实际脚本超时命令的七份序列化错误交给通知及准备详情组件；字段原因、文件位置和超时限额保留，原数据不变，引用的测试凭据不回显，摘要已含诊断时只出现一次。五种不合法配置分别再经过生产修复入口，核验同一真实原因及原文件字节保留。文件读取错误另验证原操作系统诊断及错误号。前端类型检查与隔离开发版原生编译通过，测试、开发编译及最终源码哈希一致；原生窗口仍未授权，不声称窗口验收。证据位于 `.tmp/configuration-error-feedback`。

原生只读测量在修复前记录两轮误报：25 次暂停、9 次读取产生三次格式错误；加入封闭日志捕获后，28 次暂停、6 次读取再次产生三次错误，日志明确记录 `configurationReadFailed`、`profile-store-unsupported` 和 DeepSeek 的 Claude 文件相对位置。Zhipu GLM 的同类文件也在首轮命中。两轮文件哈希完全未变。修复后同一配置副本经 52 次暂停、33 次读取零错误，哈希不变。暂停目标只取本测试创建的子进程句柄，不操作真实程序。

122 项聚焦 Rust 回归通过，包含两端脚本初始化失败仍能读取、保存和验证配置，保留已有成功缓存并记录查询失败，配置修复为零写入；真实执行的初始化与 request 超时显示原时间预算，异常值不回显。旧 `validate_persisted` 符号与存储中的 `ScriptProgram` 调用全部删除；字段契约仍由核心校验器接受或拒绝。

最终开发 API 实际执行无限初始化循环，返回 `usage-query-failed` 与“用量查询脚本执行超过 250 毫秒限额”，不发出供应商请求，不再返回配置格式错误。

最终源码隔离编译通过，修复版另完成 1,800 秒自然静置及中途重启：170 次配置快照、170 次托盘快照和 1,190 次供应商缓存读取，两个会话均就绪且存储错误为零。记录按观察起始时间隔开此前主动回放旧结构产生的合法诊断，不清除日志。停止全部自建进程后，12 个真实应用配置与两个真实客户端配置的哈希与初始相等；含凭据的隔离副本和中间已加载二进制已清理，保留日志和证据。观察期间并行产生的三份无关界面改动被保留；仅重建这三份改动前的字节即可重得测试及编译的同一源码哈希，确认本轮后端没有漂移。

修复前的开发后端已完成一小时自然静置及中途重启，177 次原生托盘快照和持续配置读取无错误；真实历史旧结构在自然观察完成后单独回放，四个文件被准确诊断、自动修复并保留逐字节原件。自然静置未触发这个负载条件，不能代替调度暂停的前后对照；最终开发后端的复编译及延长观察结果由同一忽略目录 `.tmp/configuration-source-investigation` 保留。原生窗口未授权，不声称窗口验收。

## Consequences

Claude 保存时不再通过执行脚本预先检查运行结果，与 Codex 现行存储行为统一。非空但不可运行的源程序可以作为元数据保存；用户通过既有测试查询或实际查询获取明确失败，不能把这种运行错误误称为 JSON 结构损坏。

配置有效性不再依赖运行时机器负载或脚本顶层的时间、随机行为。既有 2 MiB 内存、256 KiB 栈和 250 毫秒执行限制不变；没有通过提高阈值、缓存成功校验、吞掉错误或重写用户脚本来规避问题。
